# Technical guide

How the analysis is built, how to run it, and how it is tested. The business findings are in the [README](../README.md).

## Stack

PostgreSQL 16 in Docker, SQL for cleaning and modelling, Python for loading and simulation, Prefect 3 for scheduling, pytest and GitHub Actions for testing, Power BI Desktop for the report. Everything used is free.

## Pipeline

```
Kaggle CSVs, ingest, raw, staging (with quarantine), core star schema, marts, Power BI
                       simulation writes sim tables that feed core
                       data quality checks gate every stage
                       Prefect runs the daily refresh at 06:00
```

The full diagram and run order are in [architecture.md](architecture.md).

| Layer | Purpose |
|---|---|
| raw | CSVs exactly as delivered, every column as text |
| staging | Typed and cleaned tables. Rejected rows go to staging.quarantine with a reason code |
| core | Dimensions and facts with surrogate keys and enforced foreign keys |
| sim | Simulator output and parameters, all synthetic |
| marts | Views that Power BI reads |
| dq | Check definitions, results, and a row count log |

Every layer is dropped and rebuilt on each run, so a run can always be repeated safely.

## Run it

Requires Docker and Python 3.11 or newer.

```bash
cp .env.example .env                  # set POSTGRES_PASSWORD
python -m venv .venv
.venv/Scripts/activate                # Linux and macOS: source .venv/bin/activate
pip install -e ".[dev]"
docker compose up -d postgres
python -m sca.download                # Olist from Kaggle, needs a free token (see src/sca/download.py)
python flows/pipeline.py              # ingest, clean, model, simulate, marts, with quality gates
python -m sca.dq                      # print every check result
pytest                                # runs against a separate throwaway database
```

To try it without a Kaggle account, run `python flows/pipeline.py data/sample` against a scratch database. The sample is synthetic and contains deliberately injected bad rows. Every run rebuilds all layers, so do not point it at a database you want to keep.

Scheduling in Docker: `docker compose up -d --build` also starts the Prefect server (UI on port 4200) and a worker that runs the daily refresh on the cron schedule `0 6 * * *` in container time (UTC).

To regenerate the written outputs from the database:

```bash
python -m sca.recommend               # docs/recommendations.md
python -m sca.docs                    # docs/data_dictionary.md
python powerbi/build_pbip.py          # Power BI project
```

## Data quality

Checks are rows in dq.check, defined in `sql/90_dq`. Each returns one number and passes when it is at or below its threshold. Critical failures stop the pipeline and fail CI. Warnings are reported only.

- 54 checks across raw, staging, core and marts.
- Types covered: not null, uniqueness, referential integrity, accepted values, date logic, row count reconciliation, freshness, and KPI sanity ranges.
- The reconciliation check is critical: raw rows must equal kept rows plus quarantined rows for every table.
- A check whose SQL cannot run counts as a failure.

## Testing

72 tests, run against a separate database so real data is never touched.

- **Cleaning:** every rule fires with an exact expected count on the synthetic sample.
- **Model:** keys are unique, foreign keys hold, and revenue reconciles between layers.
- **Simulation:** stock is conserved, results are repeatable, simulated demand equals real sales, unreliable suppliers are slower.
- **KPIs:** on time rate, fulfillment, lead time statistics, turnover and days of supply are recomputed independently in pandas and compared with the SQL views.
- **Failure injection:** duplicate keys, null keys, orphan rows, negative prices, deleted rejects and lost fact rows are each introduced on purpose, and the matching check must fail.
- **Flow:** the full Prefect flow runs green, runs twice with the same result, and fails when raw data is empty.

## Power BI

Open `powerbi/SupplyChain.pbip` in Power BI Desktop. The project is plain text, generated by `powerbi/build_pbip.py` from the marts views. Setup and refresh steps are in [powerbi.md](powerbi.md). Refreshing the report after a pipeline run is manual, because scheduled refresh in the Power BI service needs a paid licence.

## Design decisions

- **Prefect over Airflow.** One light container instead of several services and several gigabytes of memory, with the same scheduled workflow idea.
- **SQL for modelling.** Transformations are plain files that run in filename order and are easy to review.
- **Rejects are data.** Nothing is silently dropped. Every rejected row is stored with a reason.
- **Simulation runs after the core order facts**, because its demand input is real sales.
- **No secrets in git.** The `.env` file and Kaggle tokens are ignored.
