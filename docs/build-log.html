Supply Chain & Inventory Performance Analytics - commands, decisions, and what each step teaches. Blue = concept worth learning; orange = a deviation from the original plan.

Phase 0-1 - Setup, Docker Postgres, raw ingest done before this session

Commands

docker compose up -d postgres
python -m venv .venv && pip install -e ".[dev]"
python -m sca.ingest            # CSV -> raw.* as TEXT, row counts to dq.run_log
Raw = untouched. Every column is TEXT so loading can never fail on a bad value. Typing and cleaning happen in the next layer, where failures are visible and logged.
  • Bulk load uses Postgres COPY (about 1M geolocation rows in seconds).
  • Ingest drops and recreates each raw table, so it is idempotent.
Phase 2 - Staging SQL, quarantine, cleaning tests sql/10_staging

Decisions

  • Each table is classified once into a temp table with a reason column; staging takes reason IS NULL, quarantine takes the rest. They cannot disagree.
  • Hard-invalid (quarantine): duplicate key, delivered before purchase, canceled with delivery date, price ≤ 0, freight < 0, orphans.
  • Soft anomalies (flag, keep): approved before purchase, carrier pickup after delivery, delivered with no date.
  • Geolocation (1M rows) is aggregated to one row per zip prefix, not rejected, and logged.
Reconciliation: raw = staged + quarantined per table. On real data: 99,441 orders - 6 quarantined = 99,435; 99,224 reviews - 6 orphans - 551 superseded = 98,667.
Why a synthetic sample? Olist cannot be redistributed, so CI uses sca.make_sample: seeded fake data with a known number of injected defects. Tests assert the exact quarantine counts, proving every rule fires.
Gotcha: a shell heredoc with quotes broke twice; I switched to writing files directly. Also a literal % in SQL (even in comments) is treated as a placeholder by psycopg - the SQL runner now escapes it.
Phase 3 - Core star schema sql/20_core_dims, 30_core_facts
  • Dimensions: date, product, supplier (= seller), customer, warehouse. Deterministic integer surrogate keys; enforced foreign keys.
  • fact_order_line (1 row per item) and fact_shipment (1 row per order, with derived days_late, is_on_time, cycle and handoff times).
On-time rule: compare dates, not timestamps. Olist estimates are midnight-only, so a 10 am delivery on the estimated day would otherwise count as late.
Sanity check against the world: real-data on-time 93.2% and 12.6-day cycle time match published Olist analyses.
Phase 4 - Simulation layer src/sca/simulate.py
  • Demand = real weekly units per product x DC. Policy = weekly-review (s, S). Lead times ~ lognormal per supplier; 15% of suppliers deliberately unreliable.
  • The policy plans with the quoted lead time but reality follows the actual distribution, so stockouts emerge instead of being injected.
Lognormal lead times are right-skewed: most deliveries near the median, a long tail of very late ones - which is why p90 matters more than the mean for safety stock.
Deviation: original order was ingest -> sim -> staging. Simulation needs real sales, which only exist after the core order facts, so it runs after core.
Tuning: first pass made even "reliable" suppliers 61% on-time (median = quoted). Centred reliable suppliers at 75-95% of quoted: 85% on-time vs 23% for unreliable.
Data problem found: Olist's last weeks (Sep-Oct 2018) are nearly empty, so "trailing 13 weeks" showed no demand. The simulation now keeps only weeks with ≥20% of median volume.
Phase 5 - Data-quality framework sql/90_dq, src/sca/dq.py
  • Checks are rows in dq.check (id, layer, severity, SQL returning one number, threshold). Pass if value <= threshold.
  • A check whose SQL errors counts as a failure. Results append to dq.result under a run id; critical failure raises DQFailure.

Break-it-on-purpose tests (each rolled back)

  • duplicate key, null key, orphan FK, negative price, deleted quarantine rows, lost fact rows, bad KPI value, dropped table
Postgres DDL is transactional, so a test can drop a constraint, corrupt data, run the check, and ROLLBACK - leaving no trace.
Phase 6 - Marts / KPI views sql/40_marts
  • Delivery KPIs by month/state, review vs lateness, supplier scorecard, inventory position, executive monthly, plus pass-through model views for Power BI.
  • Turnover = trailing-52-week COGS / average inventory value. Days of supply = on hand / trailing-13-week daily demand. At risk = days of supply < supplier p90 lead.
Independent verification: tests recompute on-time %, lead-time mean/p90/stddev, turnover and days of supply in pandas and compare to the SQL. Two implementations agreeing is stronger than one implementation passing.
Real finding: average review 4.29 on time, 2.10 when 4-7 days late.
Bug caught by tests: risk flags were NULL (not FALSE) when days of supply was undefined; fixed with COALESCE.
Phase 7 - Prefect flow, schedule, CI flows/, Dockerfile, ci.yml
python flows/pipeline.py [folder]        # run once
docker compose up -d --build             # server (UI :4200) + worker serving cron 0 6 * * *
docker compose exec prefect-worker prefect deployment run 'daily_refresh/daily-refresh-0600' --watch
  • Each DQ gate is a task; critical failure raises and fails the flow, leaving the previous marts intact.
  • CI: Postgres service container, pytest, then the flow on data/sample.
  • Verified: flow green on real data in 2.5 min; a Docker-scheduled run completed; deployment shows cron 0 6 * * *.
Why Prefect over Airflow: one small container versus several services and ~4 GB RAM; same "scheduled DAG" story.
Safety: because every layer rebuilds, never point the flow at the sample while connected to your real database - the tests use a separate _test database for this reason.

Phase 9 - Docs and recommendations README, docs/
  • python -m sca.recommend writes recommendations from the marts: weak states, worst sellers, DC rebalancing, reorder-point changes.
  • Reorder-point impact is a counterfactual: same demand and lead-time draws replayed under a p90-based policy (400 series: fill rate 88.2% -> 90.4% for +8.8% inventory value; simulated).
  • python -m sca.docs generates the data dictionary from the database catalog so it cannot drift.
Honest correction: the first draft of the rebalancing section ranked by units and made a tiny opportunity look big; it now reports value and states the opportunity is small (~5K BRL, 120 units).
